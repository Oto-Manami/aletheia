# セルフレビュー（aletheia）

プルリクエストを出す前（既存のプルリクエストに追加でコミットする前も含む）に、次の項目を順に確認する。**見つかった問題は直してから**プルリクエストを出し、運営者への報告では「レビューで見つけて直したこと」を 1〜3 行で添える。

## 1. 重複と取り込み漏れ

- 開いているプルリクエストを一覧し、同じ内容・同じファイルを扱うものが無いか確認する
  `gh api "repos/Oto-Manami/aletheia/pulls?state=open" --jq '.[] | "#\(.number) \(.head.ref) \(.title)"'`
- 直前に取り込まれたプルリクエストについて、ブランチの内容が `main` に入っているかを**ファイルの内容で**確認する
  `git diff --stat origin/<ブランチ> origin/main -- <そのブランチで変更したファイル>` が空なら取り込み済み
- ブランチの起点が最新の `main` か確認する（`git fetch` してから `git merge-base --is-ancestor origin/main HEAD`）

## 2. プロジェクトのルール（CLAUDE.md）

- 費用が発生する操作・外部のシステムへの変更・リポジトリの設定変更をしていないか
- 鍵・パスワード・接続情報を書いていないか（`gitleaks git --redact` でも確かめる）
- 実在の人物の情報をコード・テストに書いていないか
- 公開リポジトリに置いてよい内容か（収集の方法・非公開の場の情報を書いていないか）

## 3. データベースの規約

- 取り込み済みのマイグレーションを書き換えていないか（追加のみ。`sh scripts/check-migrations.sh`）
- マイグレーションを変えたら、型の定義を作り直したか（`pnpm --filter @aletheia/db gen:types`）
- 新しい表に、公開区分・行レベルセキュリティ・ポリシー・履歴と updated_at のトリガーがあるか
- 公開サイトに出す表に `public_export` のビューがあり、「`public` かつ 有料でない かつ 承認済み」と参照先の可視性を条件にしているか
- 公開用のビューに内部の列（出どころ・根拠・公開区分・保存先など）を含めていないか
- 生活圏に近い場所・家族・学業などが、既定で非公開になる形か

## 4. テスト

- 権限・公開区分・公開用の書き出しに関わる変更に、テストを足したか
- 足したテストが、守りを外したときに**失敗する**ことを一度確かめたか（条件を消して実行し、戻す）
- テストのデータは架空のものか

## 5. 品質チェック

- `pnpm check`（lint・format・typecheck）が通るか
- `pnpm test` が通るか（Docker を使えない環境では、PGroonga を入れた PostgreSQL に `reset:shim` で適用して実行する）
- プルリクエストを出した後、CI がすべて成功したか確認する

## 6. 書き方

- コメント・ドキュメント・コミットメッセージが日本語で、冗長でないか
- 識別子・キーは英語の snake_case（TypeScript は camelCase）
- 設計書（oto-manami-project）と食い違っていないか。食い違う場合は、設計書の更新が必要なことを運営者に伝える

## 7. プルリクエストの体裁

- タイトルと説明が、変更の内容と一致しているか（追加でコミットした場合は説明も更新する）
- コミットメッセージに決められた署名行が付いているか
- 既存のプルリクエストに追加でコミットした場合は、運営者に伝える
