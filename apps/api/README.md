# @aletheia/api

承認・取り込みの API。閲覧サイト（承認・修正など）と、Discord の Bot・自動の収集の処理（下書きを作る）から呼ばれる。運営者の手元のサーバー用の機械で動かし、Tailscale Funnel で公開の住所を付ける（設計書 決定記録 0022・0026）。設定はすべて環境変数で渡す。

## 起動

```sh
cp .env.example .env   # API_SERVICE_TOKEN を設定する
pnpm --filter @aletheia/api dev
```

## サーバー用の機械で動かす

収集の処理と同じ機械で、常に動かしておく（設計書 決定記録 0022）。待ち受けるのは同じ機械からだけ（`HOST=127.0.0.1`）。

専用の利用者（`aletheia`）の **systemd のユーザーサービス**（`aletheia-api`）として動かす。起動・停止・記録を見るのに管理者の権限は要らない。

1. Node.js（22 以上）と pnpm（`package.json` の `packageManager` の版）を入れ、`aletheia` の利用者でこのリポジトリを `~/aletheia` に置いて `pnpm install` する。ログアウト中も動くよう、管理者が `sudo loginctl enable-linger aletheia` を実行する
2. 環境変数を `~/.config/aletheia/api.env`（持ち主だけが読める権限 `600`）に書く。項目は `.env.example` のとおりで、`FILE_STORE=drive` にする。値はパスワード管理アプリから写し、ここにもチャットにも書かない
3. ユーザーサービスとして登録する。サービスの定義と、設定ファイルの雛形を作る手順は、自動の収集の処理のリポジトリ（非公開）の `scripts/setup-server.sh` にまとめている

```ini
# ~/.config/systemd/user/aletheia-api.service
[Unit]
Description=aletheia API

[Service]
WorkingDirectory=%h/aletheia
EnvironmentFile=%h/.config/aletheia/api.env
ExecStart=/usr/bin/env pnpm --filter @aletheia/api start
Restart=on-failure
RestartSec=10

[Install]
WantedBy=default.target
```

```sh
systemctl --user daemon-reload
systemctl --user enable --now aletheia-api
curl http://127.0.0.1:8787/health   # {"ok":true}
curl http://127.0.0.1:8787/ready    # {"ok":true}（データベースまで使える）
journalctl --user -u aletheia-api   # 記録
```

### 読み込みを軽くする仕組み

設計書 決定記録 0062。設定を書かなくても既定で動く。

- 一覧用の縮めた画像を、この機械のディスク（`THUMBNAIL_CACHE_DIR`。既定は `~/.cache/aletheia/thumbnails`）にも置き、2 回目からは Drive とデータベースに行かずに返す。消しても作り直す。大きさは 1 枚あたり数十 KB
- ログインした人の役割を `ROLE_CACHE_SECONDS`（既定 60 秒）覚える。役割の変更・参加者を外したことが API に効くまで、最大でこの時間だけ遅れる
- JSON の返事は、ブラウザが求めれば圧縮する

### 似た画像を見つける仕組み

設計書 決定記録 0069。設定を書かなくても既定で動く。

- 取り込みのとき（`POST /intake`）に、下書きの画像の見た目のハッシュ（`phash`）を仮置きのファイルから計算して付ける（振り分け待ちを除く）
- API は起動の 1 分後と、その後 6 時間ごとに、計算していない承認待ち・保留の下書きの画像と、原本を保存している画像を 1 件ずつ計算する。保存済みの画像は、計算したら似た画像を「重複の疑い」（`merge_candidates`）に入れる。止めるときは `IMAGE_HASH_JOB=off`
- 承認の画面で「同じ画像」（`same_as`）・「別の画像」（`distinct_from`）を選んだ組は、その判断で残す。選ばずに承認した画像は、似た保存済みの画像があれば「重複の疑い」に入れる
- 既にある画像どうしは `POST /duplicates/:id` で決める。どちらのファイルも消さない

### 仮置きのファイルの片付け

設定を書かなくても既定で動く（Drive を使うときだけ）。

- Bot・収集の処理は、ファイルを先に仮置きの場所（`_staging/<経路>/`）に置いてから下書きを作る。下書きを作るところで失敗すると、どの下書きにも紐付かないファイルが残る
- API は起動の 10 分後と、その後 1 日ごとに、仮置きの場所のファイルのうち、どの下書き（状態を問わない）にも紐付いておらず、置いてから `STAGING_CLEANUP_DAYS`（既定 7）日たったものを、ごみ箱に移す（Drive では 30 日間戻せる）。1 回に移すのは 500 件まで。止めるときは `STAGING_CLEANUP_JOB=off`
- 承認の後に保存できなかったファイルは、下書きが指しているので残る（`POST /posts/:id/files/retry` でやり直せる）

### 自動で更新する

`main` への取り込みで、GitHub Actions が API を最新にする（設計書 決定記録 0036。設定と、新しいマイグレーションがあるときの手順は [ops/deploy/README.md](../../ops/deploy/README.md)）。

### インターネットから届くようにする（Tailscale Funnel）

作業者が家の外から承認できるよう、API に公開の住所（`https://<機械の名前>.<tailnet>.ts.net`）を付ける（設計書 決定記録 0026）。API 自体は同じ機械からだけ受け付けたまま（`HOST=127.0.0.1`）で、Funnel が 443 番を 8787 番に渡す。SSH などほかの入口は公開しない。

1. Tailscale を入れてログインする（アカウントはプロジェクト専用のものを使う）

   ```sh
   curl -fsSL https://tailscale.com/install.sh | sh
   sudo tailscale up
   ```

2. Funnel をオンにする。初回は、管理画面で HTTPS の証明書と Funnel を有効にするための URL が表示される

   ```sh
   sudo tailscale funnel --bg 8787
   tailscale funnel status   # 公開の住所を確かめる
   ```

3. 閲覧サイト（Vercel）の環境変数 `VITE_API_URL` を、表示された `https://…ts.net` にして、デプロイし直す

止めるときは `sudo tailscale funnel --https=443 off`。Funnel を使わないときは、SSH のポート転送でサーバーの API を手元の 8787 番につないでも使える（`ssh -N -L 8787:127.0.0.1:8787 <サーバー>`。閲覧サイトの `VITE_API_URL` は `http://localhost:8787`）。

## 認証

閲覧サイトの利用者の役割は、運営者（`admin`）・作業者（`worker`）・閲覧者（`viewer`）の 3 つ（設計書 決定記録 0032）。閲覧者は見るだけで、変更（`POST`）は作業者・運営者だけ。下書きの振り分け（「言及なし」を含む）・承認・出来事の記録は作業者・運営者が扱え、印の付け直しは運営者だけ。

| 呼び出す側                      | `Authorization` ヘッダー                                          | 承認者として残るもの                                                       |
| ------------------------------- | ----------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Bot・収集の処理（下書きを作る） | `Bearer <API_SERVICE_TOKEN>`                                      | リクエストの `reviewer_id`（今の Bot・収集の処理は承認しないので使わない） |
| 閲覧サイト                      | `Bearer <ログインした利用者のトークン>`（運営者・作業者・閲覧者） | ログインした利用者                                                         |

承認済み・却下の一覧（`GET /intake?state=approved`）は、判断した新しい順に、判断した日時（`reviewed_at`）と人（`reviewed_by_name`）を返す。トーク（`message`）の下書きは、書いた人（`author`）が情報源の持ち主 1 人だけのときに限って承認できる（違えば 422、`code` は `author_mismatch`。決定記録 0068）。素材・投稿を消すエンドポイントは無い（データベースの権限でも、ログインした利用者は読み取りだけ）。

### 出来事を作る・直す

作業者・運営者が、出来事（仕事と公式の発表）を作り、直せる（設計書 決定記録 0027・0032）。消せるのは運営者と作った本人で、何も紐付いていない出来事だけ（決定記録 0030）。`GET /events/:id` は、見ている人が消せるか（`can_delete`）と、紐付いているものの数（`usage`）、紐付いた素材（`materials`。承認済みの紐付けの投稿）も返す。一覧の `has_sources` は、出典の URL か紐付いた素材のどちらかがあれば真。`GET /events/source-preview?url=` は、出典の URL に当たる取り込み済みの素材（保存済みの投稿、振り分け・承認待ちの下書き）の見出しを返す。外のサイトには取りに行かない（決定記録 0030）。URL は、書き方の違い（http/https・末尾の /・# 以降・`utm_` などの共有や計測の引数）をそろえて比べ、情報源の設定 `url_patterns` で記事の番号が分かるときは、番号でも探す（引数の違う同じ記事の URL。決定記録 0046）。人が作ったものは人の判断として、承認を経ずに入る。

| 項目                                       | 内容                                                                                                                                             |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `kind` / `event_type`                      | 出来事の種類（設計書 語彙 4 章）。`event` のときは細かい種類も                                                                                   |
| `title`                                    | 題名                                                                                                                                             |
| `starts_on` / `ends_on` / `date_precision` | JST の暦日と精度（`day` / `month` / `year`）                                                                                                     |
| `starts_at` / `ends_at`                    | 時刻が分かるときだけ（`+09:00` つき）                                                                                                            |
| `work_id` / `venue_id` / `parent_id`       | 作品（`work`）・会場（`place`）・親の出来事。親は自分と自分の下の出来事を選べない                                                                |
| `participants`                             | 出演。`entity_id`（人物かグループ）/ `role`（語彙 5 章）/ `status`（`scheduled` / `appeared` / `not_appearing` / `cancelled`）/ `character_name` |
| `sources`                                  | 出典の URL（任意）。`attributes.sources` に入る                                                                                                  |
| `classification`                           | 公開区分。既定は無く、必ず送る                                                                                                                   |

作った人・最後に直した人を `created_by` / `updated_by` に残す。直す前の状態は変更履歴（`app.history`）に、直した人とともに残る。

### 全件を取り込む経路（`state: "triage"`）

メンバーのブログのように全件を取り込む経路は、`state: "triage"`（振り分け待ち）で送る（設計書 決定記録 0021）。API が次の紐付けを規則で足す。

| 足すもの         | 内容                                                                                                                                                                                                                                                                                         |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 発信者           | 情報源の持ち主（`channels.owner_entity_id`）を `author` で紐付ける                                                                                                                                                                                                                           |
| 言及             | 蓄積対象（`entities.attributes.archive_subject = true`。人物と、その人の期）ごとに、別名が本文にあれば `mentioned`。期の `attributes.peer_aliases`（「同期」など）は、発信者がその期に属するとき（`member_of`）だけ使う。人物には画像ごとに「写っているか」の候補（`appears`、未選択）も足す |
| 登場するメンバー | タグ付けの候補（`entities.attributes.tag_candidate = true`）の名前・別名が本文にあれば、`mentioned` の候補（根拠の `purpose` は `tag`）。振り分けの判断には使わず、承認のときに人が確かめる。書いた本人と蓄積対象は除く                                                                      |

発信者が蓄積対象の人物なら、振り分けを通さず承認待ち（`pending`）から始める。結果の `state` で、どちらになったかを返す。承認待ち（`pending`）で送る下書きに同じ規則を足したいときは `apply_rules: true` を付ける（メッセージアプリの言及の通知。承認待ちのまま入れる。決定記録 0067）。振り分けで「言及なし」と確認済みの記事は 409（`checked_no_mention`）で断る。

振り分け待ちの一覧（`GET /intake?state=triage`）は、言及の強さで絞り込み・並べ替えられる。本人（蓄積対象の人物）への言及と、期などへの言及を分けて数える（登場するメンバーのタグ付けの候補は数えない）。

| 指定      | 値                                                                                                                                                                                                               |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `mention` | `all`（既定）/ `any` 言及あり / `subject` 本人への言及あり / `group_only` 期への言及だけ / `none` 言及なし / `unnamed` 言及なしのうちメンバーの名前も無い / `others_only` 言及なしのうちほかのメンバーの名前だけ |
| `source`  | `all`（既定）/ `blog` メンバーのブログ / `news` 公式サイトのニュースなど（情報源の種類が `web`）                                                                                                                 |
| `sort`    | `oldest`（既定。取り込んだ古い順）/ `signal` 本人への言及の数 → 期への言及の数 → メンバーの名前の無いもの → ほかのメンバーの名前だけのもの → 古い順                                                              |

返すもの: `items`（各記事に `subject_mentions`・`group_mentions`・`tag_mentions`（ほかのメンバーの名前の数）・`channel_kind`）、条件に当てはまる件数 `total`、条件ごとの件数 `counts`、蓄積対象の人物の ID `subject_ids`。

## ファイル

| いつ           | すること                                                                                                                                                                                                                                                                                                                      |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 取り込み       | `/files/staging` で承認待ちの場所（`_staging/<経路>/`）に保存する。`POST /intake` の `staged_files` は、その経路の承認待ちの場所にあるものだけを受け付ける（無ければ 422。設計書 決定記録 0048）                                                                                                                              |
| 承認の後       | 素材と SHA-256 が一致するファイルを本来の場所（`<情報源の種類>/<発信者>/<年-月>/<日時>_<投稿 ID>_<連番>`）へ移し、`asset_files` に原本として記録する。既に同じファイルがあれば却下の場所へ移す（`duplicate_`）。下書きの素材に無いファイル（振り分けで写っている人を付けなかった画像など）は、保存せずに消す（決定記録 0037） |
| 却下の後       | 却下の場所（`_rejected/<経路>/`）へ移す（削除しない）                                                                                                                                                                                                                                                                         |
| 素材を外した後 | `POST /assets/:id/remove` で外した素材の原本を、却下の場所（`_rejected/removed/<素材の ID>_<種類>.<拡張子>`）へ移す（削除しない。決定記録 0045）                                                                                                                                                                              |

仮置きのファイルを動かす・消す前には、仮置きの場所にあるかを確かめ直し、無いものには触らない。消すときはごみ箱に移す（決定記録 0048）。移動に失敗しても承認は取り消さず、結果の `files.failed` で返す（データ品質の検査でも見つかる）。閲覧サイトは承認の画面で知らせ、投稿の画面の「ファイルの保存をやり直す」（`POST /posts/:id/files/retry`）でやり直せる。どの下書きにも紐付いていない古い仮置きのファイルは、1 日 1 回ごみ箱に移す（上の「仮置きのファイルの片付け」）。保存先は `FILE_STORE`（`drive` / `local`）で選ぶ。Drive へは専用アカウントの OAuth で接続する（決定記録 0001）。

## エラー

| 状態      | 意味                                                                                                               |
| --------- | ------------------------------------------------------------------------------------------------------------------ |
| 400       | リクエストの形が正しくない                                                                                         |
| 401 / 403 | 鍵・ログインが無い / 役割が足りない（閲覧者の変更、運営者だけの操作）                                              |
| 404       | 下書きが見つからない                                                                                               |
| 409       | 同じ下書きが既にある・既に承認か却下されている                                                                     |
| 422       | 下書きの形が正しくない（`invalid_draft`）、存在しない人物などを指している（`reference`）、情報源が登録されていない |
